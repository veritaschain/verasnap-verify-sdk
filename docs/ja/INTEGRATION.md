# 損害保険会社向け導入ガイド

## 位置づけ

事後検知（AI生成画像の判定、使い回しの照合）は、すべての写真に、契約者の手間なしでかけられますが、結果は確率です。撮影時証明は、封印カメラで撮った写真にしか効かず、契約者に一手間かかりますが、結果は「一致するか、しないか」で、画像生成AIが進化しても弱くなりません。両者は代替ではなく、直列につなぎます。

| 段階 | 対象の写真 | 確認方法 | 結果 |
|---|---|---|---|
| 1 | 登録済みの鍵による証明付き | `Verifier.verify(proof, photo)` | 緑：ファストトラック／黄・赤：段階2か3へ |
| 2 | 証明なし（カメラロール、LINE、Web） | 既存の事後検知 | 現行どおり |
| 3 | 疑義案件、高額案件 | 保険会社アプリの撮影SDKで撮り直しを依頼 | 段階1と同じく検証 |

段階3の必須化を必要な案件だけに絞れば、大半の請求では契約者の手続きは変わりません。

## 最小構成

1. 請求アプリや受付チャネルから、証明と写真を受け取る（共有用JSON、`proof.json`、Evidence Pack ZIPのいずれか）。
2. `result = Verifier(registry=…).verify(proof, photo)` を呼ぶ。
3. `result.to_dict()` を請求に紐づけて保存する。チェック内容、検証済みのタイムスタンプ、署名鍵、SDKのバージョンが残ります。
4. `result.level` で振り分け、必要に応じて `(check.id, check.code)` で詳しく分岐する。

結果は支払担当者への参考情報であり、自動判定ではありません。緑は「登録済みの端末で撮影時に封印されたファイルそのものである」ことを示しますが、損傷が本物であることは示しません。

## 振り分けの例

| 結果 | よくある意味 | 対応例 |
|---|---|---|
| 緑 | 登録済み端末で撮影時に封印、変更なし、60分以内にタイムスタンプ取得 | ファストトラック。この写真には事後検知AIをかけない |
| 黄 `signer_key/unknown` | 証明は有効だが、登録していない鍵（消費者向けアプリ、または偽造者自身の鍵） | 証明なしの写真と同じ扱い（段階2） |
| 黄 `capture_time/anchor_delayed` | オフライン撮影、または撮影時刻のさかのぼり。タイムスタンプの時刻には存在していた | タイムスタンプの時刻と申告された事故日を比べる |
| 黄 `timestamp/untrusted_chain` | 信頼リストにないTSA | 信頼リストを見直す。そうでなければ段階2 |
| 赤 `media_hash/mismatch` | 封印後に写真が編集・再圧縮・差し替えされた | 原本の提出を求める。繰り返すなら調査へ |
| 赤 署名・EventHash・タイムスタンプの不合格 | 証明が改変された、または剥がされた | 調査へ |

## データとプライバシー

- 検証はオフラインで、証明とファイルだけで行います。画像を社外に出す必要はありません。
- 鍵の台帳に保存するのは、公開鍵、証明の要約、保険会社が決める参照ID（`account_ref`）だけです。生体情報は含みません。VeraSnapの生体認証は「実施したこと」と方式・結果だけを記録し、撮影者を特定しません。
- 証明の中の位置情報は、署名済みイベントにはハッシュとして入っています。正確な座標は、利用者が共有を選んだ内部用エクスポートにだけ含まれます。

## 運用

- SDKの信頼データを最新に保ってください。Googleは鍵証明のルートを更新することがあります（現在2つを同梱）。TSAのルートは `src/verasnap_verify/data/README.md` にあります。
- Android端末を登録する場合は、Googleの証明書失効リストを毎日取得してください。
- 端末の紛失や契約終了時は鍵を失効させてください（`registry.revoke(fingerprint, reason)`）。失効した鍵の証明は黄になります。
- 本番ではSDKのバージョンを固定し、判断ごとに `result.sdk_version` と `result.rules` を記録してください。
